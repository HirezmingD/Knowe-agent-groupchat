## 24 种角色表

成员（Worker）一共有 24 种角色，每种对应一类专业判断。下表「擅长」= 这类判断交给他最省心，「不适合」= 这类判断交给他大概率跑偏——两者都是**分工建议**，不是能力排行榜（解读见[常见误区](#常见误区擅长与不适合不是能力判决)）。

| 角色 | 前缀 / id¹ | 擅长 | 不适合 |
|:--|:--|:--|:--|
| **前端** | — | 浏览器行为、状态管理、样式细节与页面交互 | 服务端架构与数据层判断 |
| **后端** | — | 服务端逻辑、接口设计、数据流与系统集成 | 视觉、交互与文案调性判断 |
| **产品** | — | 定义问题、梳理需求优先级、权衡用户价值 | 具体实现细节（代码 / 样式）判断 |
| **测试** | — | 设计用例、找边界场景、质疑「哪些会出错」 | 品牌调性与创意方向判断 |
| **UI/UX 设计** | — | 用户路径、视觉层次、一致性 | 纯逻辑与算法实现判断 |
| **数据分析** | — | 整理数据、统计分类、找规律、画图表 | 主观创意与文案表达判断 |
| **运维** | — | 部署、环境、依赖与变更管理 | 产品定位与用户研究判断 |
| **安全** | — | 威胁模型、漏洞面、风险与合规边界 | 界面视觉与交互判断 |
| **AI / 机器学习** | — | 模型选型、数据准备、训练与评估 | 业务文案与运营判断 |
| **移动端** | — | 移动平台行为、适配、性能与发布 | 服务端架构与数据层判断 |
| **游戏** | — | 玩法、数值、关卡与游戏循环 | 严肃文档与合规判断 |
| **地理信息** | — | 空间数据、坐标系、地图与空间分析 | 品牌营销与文案创意判断 |
| **营销** | — | 受众、转化目标与传播策略 | 代码实现与系统架构判断 |
| **金融 / 财务** | — | 成本、口径、财务逻辑与合规风险 | 创意设计与交互体验判断 |
| **医疗** | — | 医疗场景术语、流程与合规敏感性 | 互联网产品增长与运营判断 |
| **学术 / 教育** | — | 知识组织、教学结构、引用规范 | 工程实现与性能优化判断 |
| **空间计算** | — | 3D 空间交互、空间设计与人机边界 | 传统文档与合规判断 |
| **技术支持** | — | 用户问题定位、话术与解决路径 | 产品战略与架构决策判断 |
| **站点可靠性** | — | 故障面、依赖链、恢复顺序与可靠性 | 内容创作与品牌表达判断 |
| **数据库** | — | 数据模型、查询优化、迁移与一致性 | 界面交互与视觉判断 |
| **架构** | — | 系统拆分、技术选型、权衡取舍 | 细颗粒度执行（具体页面 / 文案）判断 |
| **技术写作** | — | 搭文档结构、把信息组织清楚、成文 | 运营增长与投放策略判断 |
| **音视频** | — | 音视频处理、格式、剪辑与媒体验收 | 财务与合规判断 |
| **法务 / 合规** | — | 措辞风险与合规边界 | 前端交互与产品创意判断 |

¹ 「前缀 / id」是产品内部对成员角色的标识，界面中以成员名字与角色标签为准；具体值随版本发布、以产品实际为准，本页不臆造。

## 怎么挑角色：决策建议

按下面几条，不用背表也能挑对人：

1. **先让项目经理提议，你确认即可**——组建团队卡和派发任务卡上都带候选成员的「擅长」说明，选人判断先交给项目经理，你把关（见[20 使用指南 · 创建项目与组建团队 · 第 4 步](20-01-创建项目与组建团队.md#第-4-步--确认团队卡组队)）；
2. **挑的是「这活该谁来想」**——先问需求的核心是什么类型的判断：用户与体验 → UI/UX 设计、产品；逻辑与实现 → 前端、后端、架构；数据与事实 → 数据分析、数据库；风险与合规 → 安全、法务；表达与组织 → 技术写作、营销（详见[10 核心概念 · 为什么派活要按角色挑人](10-02-知知-项目经理-成员.md#为什么派活要按角色挑人)）；
3. **尊重「不适合」边界**——让法务去写前端交互、让测试去定品牌调性，不是「做不到」，而是判断方向大概率不对，返工成本更高；
4. **第一次不必凑满**——角色可以随时再加（让项目经理提议，你确认一张团队卡即可，见[20 使用指南 · 管理团队 · 加人](20-02-管理团队.md#加人让项目经理提议)）；
5. **想自己挑人时**——花名册与成员资料页（擅长领域、当前状态、权限边界）就是决策依据（见[20 使用指南 · 搜索、收藏与联系人 · 联系人资料页](20-07-搜索收藏与联系人.md#联系人资料页)）。

一个把「判断类型 → 角色」落地的对照（摘自已发布页面）：

| 场景 | 交给谁 | 为什么 |
|:--|:--|:--|
| 写一个带交互的页面 | 前端成员 | 判断力在浏览器行为、状态管理、样式细节 |
| 定信息架构与视觉规范 | UI/UX 设计成员 | 判断力在用户路径、层次、一致性 |
| 排查线上服务不可用 | 站点可靠性 / 运维成员 | 判断力在故障面、依赖链、恢复顺序 |
| 起草一份合规声明 | 法务成员 | 判断力在措辞风险与合规边界 |
| 出产品调研报告 | 产品 / 数据分析成员 | 判断力在问题定义与证据解读 |

## 常见误区：擅长与不适合不是能力判决

- **不是能力排行榜**——「擅长」不是「只有他能干」，「不适合」也不是「他干不了」；两者描述的是**判断方向**：交给谁最省心、交给谁大概率跑偏（见[10 核心概念 · 工具一样，脑子不一样](10-02-知知-项目经理-成员.md#工具一样脑子不一样)）；
- **工具一样，脑子不一样**——成员的工具箱完全相同（读写文件、运行命令、联网查证、调用模型），差别只在专业判断——所以挑人挑的是判断力，不是工具箱；
- **角色标签不是固定分工**——同一角色在不同项目里干的活由需求决定；具体派给谁，以项目经理的提议和你的确认为准。

## 与产品内角色目录的关系

- 上表角色名与**产品内角色目录一致**（前端、后端、产品、测试、UI/UX 设计、数据分析、运维、安全、AI / 机器学习、移动端、游戏、地理信息、营销、金融 / 财务、医疗、学术 / 教育、空间计算、技术支持、站点可靠性、数据库、架构、技术写作、音视频、法务 / 合规——以产品实际为准）；
- 表格中的「前缀 / id」、角色标签的精确措辞、界面中的「擅长 / 不适合」文案随版本发布、以产品实际为准——本页只给文档口径的速查，不臆造内部标识；
- 成员名字（如「江澈」「顾言」）是随项目生成的名字，与角色是两个维度：**名字不翻译、头像终身绑定**（见[10 核心概念 · 成员](10-02-知知-项目经理-成员.md#成员24-种角色可增可减)），角色名随界面语言翻译（见[30 配置 · 外观与界面语言 · 角色名随语言翻译，成员名字不翻译](30-03-外观与界面语言.md#角色名随语言翻译成员名字不翻译)）。
